# Модули: ESM и CommonJS

## Главное различие

**ESM статичен, CommonJS динамичен.**

`import`/`export` разбираются на этапе парсинга, до исполнения кода. Поэтому сборщик
знает граф зависимостей заранее — отсюда tree shaking и проверка опечаток в импортах
на этапе сборки.

`require()` — обычный вызов функции во время исполнения: путь можно собрать из переменной,
модуль можно подключить условно, но статически проанализировать это нельзя.

```js
// ESM — только на верхнем уровне, путь только литерал
import { helper } from './helper.js';

// CommonJS — где угодно, путь любой
if (needed) {
  const helper = require(`./helpers/${name}`);
}
```

| | ESM | CommonJS |
| --- | --- | --- |
| Разбор | статически | в рантайме |
| Экспорт | живые биндинги | копия значения |
| Загрузка | асинхронная | синхронная |
| `this` на верхнем уровне | `undefined` | `module.exports` |
| Режим | всегда strict | по умолчанию sloppy |
| Tree shaking | да | практически нет |

## Три фазы загрузки ESM

1. **Construction** — по графу импортов найти и скачать все модули, распарсить.
2. **Instantiation** — создать области модулей, связать импорты и экспорты ссылками
   (память выделена, значения ещё не вычислены).
3. **Evaluation** — выполнить тела модулей снизу вверх по графу, заполнить значения.

Разделение фаз объясняет и hoisting импортов, и работу циклических зависимостей.

## Живые биндинги

Импорт — это **ссылка на переменную** в модуле-источнике, а не копия значения.

```js
// counter.js
export let count = 0;
export function increment() {
  count += 1;
}

// main.js
import { count, increment } from './counter.js';
console.log(count); // 0
increment();
console.log(count); // 1 — значение обновилось само
count = 5;          // TypeError: Assignment to constant variable — импорт только для чтения
```

В CommonJS было бы `0` и `0`: `require` копирует значение в момент вызова.
(Объекты копируются по ссылке, поэтому мутация полей видна — но переприсваивание нет.)

## Импорты поднимаются

```js
greet();                       // работает
import { greet } from './greet.js';
```

Все импорты обрабатываются до выполнения тела модуля. Побочный эффект: если импорт
нужен только ради side effect в определённом месте, порядок строк вам не поможет.

## Циклические зависимости

ESM их переживает — за счёт того, что биндинги связаны до вычисления:

```js
// a.js
import { b } from './b.js';
export const a = 'A';
console.log('a.js видит b =', b);

// b.js
import { a } from './a.js';
export const b = 'B';
console.log('b.js видит a =', a); // ReferenceError: a в TDZ
```

Если точка входа `a.js`, то сначала выполнится `b.js`, а `a` там ещё не инициализирована.
Функции в таком случае работают (они поднимаются целиком), а `const`/`let` — нет.
Вывод для собеседования: цикл не падает сразу, но порядок вычисления делает код хрупким,
и лечится это выделением общего модуля.

## Именованный и default экспорт

```js
export const a = 1;
export function f() {}
export { a as renamed };

export default class Widget {}
```

`export default` — это по сути именованный экспорт с именем `default`. Поэтому:

```js
import Whatever from './widget.js';           // имя произвольное
import { default as Widget } from './widget.js'; // то же самое
```

Практический аргумент против `default`: имя не фиксировано, поэтому по проекту
расползаются разные названия одного и того же, а автоимпорт и рефакторинг работают хуже.
Многие команды используют только именованные экспорты.

Реэкспорт:

```js
export * from './utils.js';           // всё, кроме default
export { default as Button } from './Button.js';
```

## Динамический import()

```js
const module = await import('./heavy.js');   // возвращает промис с namespace-объектом
module.default;
```

Это выражение, а не инструкция: путь может быть переменной, вызов — условным.
На этом строится code splitting:

```jsx
const Chart = React.lazy(() => import('./Chart'));
```

Сборщик видит `import()` и выделяет отдельный чанк, который грузится по требованию.

## Tree shaking

Работает при трёх условиях: ESM, статические импорты и отсутствие побочных эффектов.

```js
import { debounce } from 'lodash-es';  // вытащит только debounce
const _ = require('lodash');           // вытащит всё
```

Поле `"sideEffects": false` в `package.json` разрешает сборщику выбрасывать
неиспользуемые модули целиком. Если в пакете есть модули, импортируемые ради эффекта
(например, CSS), их перечисляют явно: `"sideEffects": ["*.css"]`.

Что мешает tree shaking: реэкспорт всего через баррель-файлы с побочными эффектами,
динамические обращения к свойствам namespace-импорта, классы с побочными эффектами
в теле модуля.

## В браузере и в Node

```html
<script type="module" src="app.js"></script>
```

Модульный скрипт по умолчанию `defer`, исполняется в strict mode, имеет свою область
(`var` на верхнем уровне не попадает в `globalThis`), грузится с CORS-правилами.

В Node тип модуля определяется полем `"type"` в `package.json` (`"module"` или `"commonjs"`)
либо расширением `.mjs` / `.cjs`. В ESM нет `__dirname` и `__filename` — вместо них
`import.meta.url`, `import.meta.dirname` и `import.meta.filename`.
