# Что и как тестировать

## Пирамида против testing trophy

**Пирамида** (классика бэкенда): много юнит-тестов, меньше интеграционных, мало E2E.

**Testing trophy** (Kent C. Dodds, для фронтенда):

```
        E2E          — немного, критические пути
   Интеграционные    — больше всего: компоненты и сценарии
      Юнит-тесты     — чистая логика
 Статический анализ  — TypeScript, ESLint
```

Логика: во фронтенде ошибки чаще всего на **стыке** — компонент + хук + стор + запрос.
Юнит-тест маленькой функции может проходить, а экран — не работать. Интеграционный
тест компонента с замоканной сетью проверяет то, что видит пользователь, и остаётся
быстрым.

## Что действительно даёт уверенность

- **Чистая логика** — юнит-тестами, подробно, с граничными случаями: форматирование,
  валидация, расчёты цены, редьюсеры, маппинг ответов API.
- **Сценарии экранов** — Testing Library: пользователь вводит, кликает, видит результат;
  сеть через MSW — включая ошибки, пустые ответы, медленную загрузку.
- **Сложные кастомные хуки** — `renderHook`.
- **Критические пути** — несколько E2E (Playwright): вход, оплата, оформление заказа.
- **Всё остальное** закрывают TypeScript и линтер.

Что не стоит тестировать: сторонние библиотеки, простую разметку без логики, реализацию
(state, классы), «на всякий случай» большие снапшоты.

## Покрытие и его пределы

Покрытие показывает, какие строки **выполнились** в тестах, но не то, что они **проверены**.
100% покрытия возможны без единого осмысленного `expect`.

- Полезно как индикатор **непокрытых** мест: обработчик ошибки, ветка `else`.
- Вредно как KPI: команда пишет тесты ради процента, тестирует тривиальное.
- Разумно: высокий порог для слоя бизнес-логики, без жёсткого процента для UI.

Качество тестов проверяет **мутационное тестирование** (Stryker): инструмент вносит
мелкие изменения в код — если тесты не упали, они слабые.

## Регрессионный тест на каждый баг

Нашли баг → сначала пишем тест, который его **воспроизводит** (и падает), потом
исправляем (тест проходит). Так баг не вернётся, а тест документирует случай, который
кто-то уже однажды сломал. Особенно ценно для гонок, граничных случаев и
«исправили в одном месте — сломали в другом».

## Тестирование в CI

- Тесты, типы и линтер — **на каждый pull request**; мёрж только при зелёном CI.
- Юнит и интеграционные — быстро, на каждый коммит; E2E — на PR или перед релизом,
  параллельно и с ретраями только для доказанно нестабильных сценариев.
- **Flaky-тесты** — лечить или удалять: тест, который иногда падает, учит команду
  игнорировать красный CI. Причины: зависимость от порядка, реальное время, сеть,
  общие данные между тестами, ожидание фиксированным `sleep` вместо условия.
- Артефакты падений E2E: скриншоты, видео, трейсы Playwright.

## Как это спрашивают

- «Что вы тестируете и что — нет?»
- «Пирамида или трофей? Почему?»
- «Нужно ли 100% покрытие?»
- «Как вы боретесь с нестабильными тестами?»
- «Что делаете, когда находите баг?» — регрессионный тест.
