# Keys и списки

## Как React сравнивает списки

Когда компонент возвращает массив детей, React должен понять, как новый список
соотносится со старым: какие элементы остались, какие переместились, какие новые.

- **Без ключей** — сопоставление по позиции: старый 0-й с новым 0-м и т. д.
- **С ключами** — по `key`: элемент с ключом `"a"` в старом списке — тот же, что
  с ключом `"a"` в новом, где бы он ни стоял.

Ключ — это **идентичность элемента между рендерами**. С одинаковым ключом React
переиспользует DOM-узел, state компонента и его эффекты; с новым ключом — создаёт
заново; пропавший ключ — размонтирует.

Ключ должен быть уникальным **среди соседей**, не глобально. И он не передаётся
в компонент как проп — `props.key` будет `undefined`.

## Баг с key={index}

```jsx
function TodoList() {
  const [todos, setTodos] = useState([{ id: 1, text: 'Молоко' }, { id: 2, text: 'Хлеб' }]);
  const addFirst = () => setTodos([{ id: 3, text: 'Сыр' }, ...todos]);

  return todos.map((todo, index) => (
    <li key={index}>
      {todo.text} <input placeholder="заметка" />
    </li>
  ));
}
```

Пользователь написал заметку «2 литра» у «Молоко» и нажал «добавить первым». Теперь
у «Сыр» ключ `0` — тот же, что был у «Молоко». React решает, что элемент с ключом `0`
просто изменил текст, и **переиспользует его DOM** — неконтролируемый `<input>` со
значением «2 литра» остаётся в первой строке, рядом с «Сыр».

Проявления того же бага: пропадающий фокус, анимации не у тех элементов, открытое
меню «перепрыгивает» к соседу, чекбоксы переключаются не там.

С контролируемыми полями баг часто скрыт — но проявится при первом появлении
локального state в элементе (режим редактирования, раскрытие).

Когда индекс допустим: список **никогда** не меняет порядок, в нём нет вставок и удалений,
у элементов нет своего state (например, статичный список пунктов меню).

## Почему не Math.random()

```jsx
items.map((item) => <Row key={Math.random()} item={item} />)
```

Ключ новый на каждом рендере → React считает все элементы новыми → **размонтирует
и заново монтирует весь список** при любом обновлении. Теряется state, фокус,
перезапускаются эффекты (и запросы в них), страдает производительность.

## Откуда брать ключи

1. **id из данных** — лучший вариант (id записи из БД).
2. Если данных без id — **сгенерировать при создании** элемента, а не при рендере:
   `{ id: crypto.randomUUID(), text }` в обработчике добавления.
3. Составной ключ из стабильных полей, если они уникальны: `` `${date}-${userId}` ``.

## Ключ вне списков: сброс состояния

`key` работает для любого элемента. Смена ключа = новый экземпляр компонента:

```jsx
<ProfileForm key={userId} user={user} />
```

Выбрали другого пользователя → старая форма размонтируется, новая смонтируется
с чистым state из `useState(user.name)`. Это рекомендованная замена антипаттерну:

```jsx
// плохо: лишний рендер со старыми данными, легко забыть поле
useEffect(() => {
  setName(user.name);
  setEmail(user.email);
}, [user.id]);
```

## Списки и производительность

- Хорошие ключи позволяют React **переставлять** DOM-узлы вместо пересоздания.
- Для длинных списков (тысячи строк) ключи не помогут: рендерить всё — дорого.
  Нужна **виртуализация** (`@tanstack/react-virtual`, `react-window`): в DOM только
  видимые строки.
- Строки списка часто оборачивают в `memo`, но это работает, только если пропсы
  стабильны (объекты из данных — те же ссылки, колбэки через `useCallback`).

## Как это спрашивают

- «Зачем нужны ключи?» — идентичность элемента при сравнении списков.
- «Почему нельзя использовать индекс?» — нужен конкретный пример с неконтролируемым
  input или локальным state.
- «Что будет с `Math.random()` в ключе?»
- «Как сбросить state компонента при смене пропса?» — `key`.
- «Должен ли ключ быть глобально уникальным?» — нет, среди соседей.
