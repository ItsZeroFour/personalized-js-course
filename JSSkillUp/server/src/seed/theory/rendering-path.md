# Критический путь рендеринга

## От HTML до пикселей

1. **Парсинг HTML → DOM.** Парсер идёт по байтам документа и строит дерево узлов.
   Параллельно **preload scanner** заранее находит `<link>`, `<script>`, `<img>` и начинает
   их загрузку.
2. **CSS → CSSOM.** Из всех стилей строится дерево правил.
3. **Render tree** = DOM + CSSOM, только видимые узлы (`display: none` в него не попадает,
   `visibility: hidden` — попадает).
4. **Layout** (reflow) — вычисление геометрии: размеры и позиции каждого блока.
5. **Paint** — отрисовка пикселей: текст, цвета, тени, изображения — по слоям.
6. **Composite** — сборка слоёв в итоговый кадр, обычно на GPU.

## Что блокирует

**CSS блокирует рендеринг.** Браузер не покажет страницу, пока не загрузит и не разберёт
CSS из `<head>` — иначе был бы кадр без стилей (FOUC).

**Обычный `<script>` блокирует парсинг.** Скрипт может изменить DOM (`document.write`) —
парсер останавливается, ждёт загрузки и выполнения. Кроме того, скрипт ждёт CSS,
стоящий перед ним: он может читать стили.

```html
<script src="app.js"></script>          <!-- блокирует парсинг -->
<script src="app.js" defer></script>    <!-- параллельная загрузка, выполнение после парсинга, по порядку -->
<script src="stats.js" async></script>  <!-- выполнение сразу по загрузке, порядок не гарантирован -->
<script type="module" src="app.js"></script> <!-- ведёт себя как defer -->
```

`defer` — для кода приложения, `async` — для независимых скриптов (аналитика).

## Ускорение первого показа

- **Меньше блокирующего CSS**: критический CSS для первого экрана — инлайн, остальное
  грузится без блокировки; не импортировать огромные CSS-библиотеки целиком.
- **`defer` / модули** для скриптов, код-сплиттинг, меньше JS.
- **Ресурсные подсказки**: `<link rel="preload">` для шрифтов и LCP-картинки,
  `preconnect` к сторонним доменам (CDN, API), `fetchpriority="high"` для главного изображения.
- **SSR/SSG**: первый HTML уже содержит контент, а не пустой `<div id="root">`.

## Что вызывает reflow

Layout пересчитывается при изменении геометрии: размеров, отступов, шрифтов, содержимого,
добавлении/удалении элементов, изменении окна. Затем обычно нужен и paint.

**Layout thrashing** — чередование записи стилей и чтения геометрии:

```js
// плохо: каждое чтение offsetWidth заставляет браузер синхронно пересчитать layout
for (const item of items) {
  item.style.width = container.offsetWidth / 2 + 'px';
}

// хорошо: одно чтение, затем только записи
const half = container.offsetWidth / 2;
for (const item of items) item.style.width = half + 'px';
```

Свойства, чтение которых форсирует layout: `offsetWidth/Height/Top`, `clientWidth`,
`scrollTop`, `getBoundingClientRect()`, `getComputedStyle()`. В React такие измерения
делают в `useLayoutEffect`, группируя чтения.

## Слои и composite-only анимации

Изменение `transform` и `opacity` (для элемента на отдельном слое) **не требует layout
и paint** — только composite, который выполняется в отдельном потоке и не зависит от
загрузки main thread. Поэтому анимации делают на них:

```css
/* плохо: layout + paint на каждом кадре */
.panel { transition: left 0.3s; }
/* хорошо: только composite */
.panel { transition: transform 0.3s; }
```

`will-change: transform` заранее выносит элемент на свой слой. Злоупотреблять нельзя:
каждый слой — память GPU.

Для визуальных обновлений из JS — `requestAnimationFrame`: колбэк выполняется перед
следующей отрисовкой, чтения и записи группируются в один кадр.
