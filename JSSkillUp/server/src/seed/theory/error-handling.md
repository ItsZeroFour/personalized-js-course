# Обработка ошибок

## Два вида ошибок

- **Ошибки рендера** — исключение при рендере компонента (обращение к `undefined`,
  баг в данных). Без обработки React размонтирует всё дерево — белый экран.
- **Ошибки данных и действий** — сеть недоступна, сервер ответил 500, валидация не прошла,
  нет прав. Это **ожидаемые** ситуации, часть сценария.

Разные виды — разные инструменты.

## Error boundaries и fallback

Границы ошибок ловят ошибки рендера своего поддерева и показывают запасной UI.
Ставить их нужно **по зонам**:

```jsx
<ErrorBoundary FallbackComponent={AppCrash}>            {/* корень: последний рубеж */}
  <Layout>
    <ErrorBoundary FallbackComponent={PageError} resetKeys={[location.pathname]}>
      <Routes>…</Routes>                                 {/* страница упала — меню живо */}
    </ErrorBoundary>
  </Layout>
</ErrorBoundary>

<ErrorBoundary fallback={<WidgetUnavailable />}>
  <RevenueChart />                                        {/* виджет упал — дашборд живёт */}
</ErrorBoundary>
```

Fallback даёт действие: «Попробовать снова» (reset), «На главную», «Перезагрузить».
Не ловят: обработчики событий, асинхронный код — их обрабатывают отдельно или
пробрасывают в границу (`showBoundary`, `throwOnError` в TanStack Query).

## Состояния loading / empty / error

Каждый экран с данными — это как минимум четыре состояния:

```jsx
function OrdersList() {
  const { data, isPending, isError, error, refetch } = useOrders();

  if (isPending) return <OrdersSkeleton />;
  if (isError) return <ErrorState message={toUserMessage(error)} onRetry={refetch} />;
  if (data.length === 0) return <EmptyState action={<Link to="/catalog">В каталог</Link>} />;
  return <OrdersTable orders={data} />;
}
```

Частые ошибки: забытый empty state (пустая таблица без объяснения), бесконечный спиннер
при ошибке, ошибка «прячется» в консоль. Удобно моделировать discriminated union:
`{ status: 'loading' } | { status: 'error', error } | { status: 'success', data }` —
невозможные комбинации не выразимы.

## Ошибки HTTP

- `fetch` **не отклоняет** промис на 4xx/5xx — проверять `response.ok` и бросать свою ошибку.
- Единый HTTP-клиент нормализует ошибки в один тип:
  `{ status, code, message, details }` — UI не разбирает сырые ответы.
- Различать: **401** — разлогинить или обновить токен; **403** — «нет доступа»; **404** —
  страница «не найдено»; **422** — ошибки полей формы; **429** — подождать; **5xx** и сеть —
  повторить.

## Ретраи и деградация

- **Повтор** временных ошибок (сеть, 5xx, 429) с экспоненциальной задержкой и jitter.
  Не повторять 4xx: ответ не изменится. TanStack Query повторяет 3 раза по умолчанию.
- **Мутации** повторять осторожно: неидемпотентный POST может выполниться дважды.
- **Graceful degradation**: не загрузились рекомендации — страница товара всё равно
  работает; упал сервис аватаров — показать инициалы; нет сети — показать кеш с пометкой
  «данные могут быть устаревшими».
- **Оптимистичные обновления** откатываются при ошибке с понятным уведомлением.

## Логирование и мониторинг

- Ошибки рендера — `componentDidCatch` / `onError` у границы, в React 19 — `onCaughtError`
  и `onUncaughtError` у `createRoot`.
- Глобально — `window.addEventListener('error')` и `'unhandledrejection'`.
- Отправка в **Sentry** (или аналог) с контекстом: пользователь, маршрут, версия релиза,
  breadcrumbs (что происходило до ошибки), source maps для читаемых стеков.
- Не логировать ожидаемое как ошибки (404 по битой ссылке, отменённые запросы) —
  иначе мониторинг зашумлён.
- Пользователю — человеческое сообщение и действие; разработчику — стек и контекст.
  Никогда не показывать пользователю сырой стек или ответ сервера.
