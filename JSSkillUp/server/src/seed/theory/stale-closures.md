# Stale closures и ловушки хуков

## Механика: каждый рендер — своё замыкание

Функциональный компонент вызывается на каждый рендер. Пропсы и state внутри — константы
**этого** вызова. Любая функция, созданная в рендере (обработчик, колбэк эффекта,
таймера, подписки), — замыкание над константами своего рендера.

Пока функция живёт не дольше рендера (обычный `onClick`, пересоздаваемый каждый раз),
всё хорошо. Проблема — **stale closure** — возникает, когда функция переживает свой
рендер и продолжает читать устаревшие значения.

## Классика: setInterval

```jsx
function Timer() {
  const [seconds, setSeconds] = useState(0);

  useEffect(() => {
    const id = setInterval(() => {
      setSeconds(seconds + 1); // seconds навсегда 0
    }, 1000);
    return () => clearInterval(id);
  }, []);

  return <p>{seconds}</p>;
}
```

Эффект выполнился один раз — в первом рендере, где `seconds = 0`. Колбэк интервала
замкнул этот `0`. Каждую секунду он ставит `0 + 1 = 1`: таймер застывает на 1.

Где ещё встречается:

- подписки (`socket.on('message', …)`) в эффекте с пустыми зависимостями;
- `useCallback` / `useMemo` с неполными зависимостями;
- асинхронный код: после `await` переменные всё ещё из рендера, где запрос начался;
- обработчики, переданные сторонней библиотеке один раз при инициализации.

## Способ 1: функциональная форма setState

```jsx
setSeconds((s) => s + 1);
```

Колбэку больше не нужно читать `seconds` — React передаёт актуальное значение.
Лучший вариант, когда нужно только обновить state на основе предыдущего.

## Способ 2: честные зависимости

```jsx
useEffect(() => {
  const id = setInterval(() => setSeconds(seconds + 1), 1000);
  return () => clearInterval(id);
}, [seconds]);
```

Работает, но интервал пересоздаётся каждую секунду — для таймера это сбивает фазу.
В других случаях (подписка, зависящая от `roomId`) пересоздание — именно то, что нужно.

## Способ 3: ref с актуальным значением

Когда колбэк не должен пересоздаваться, но должен видеть свежие данные:

```jsx
function Chat({ roomId, onMessage }) {
  const onMessageRef = useRef(onMessage);
  useLayoutEffect(() => {
    onMessageRef.current = onMessage; // всегда последний обработчик
  });

  useEffect(() => {
    const connection = connect(roomId);
    connection.on('message', (msg) => onMessageRef.current(msg));
    return () => connection.disconnect();
  }, [roomId]); // переподключаемся только при смене комнаты
}
```

Это паттерн «latest ref». На нём построен `useEffectEvent` (экспериментальный API React):
функция, которая всегда видит последние пропсы и state, но не является зависимостью эффекта.

Классический `useInterval` Дэна Абрамова устроен так же: колбэк в ref, интервал создаётся
один раз.

## Способ 4: useReducer

```jsx
const [state, dispatch] = useReducer(reducer, initial);
useEffect(() => {
  const id = setInterval(() => dispatch({ type: 'tick' }), 1000);
  return () => clearInterval(id);
}, []);
```

`dispatch` стабилен, а актуальный state читается внутри редьюсера — замыкать нечего.

## useCallback с пустыми зависимостями

```jsx
const handleSave = useCallback(() => {
  api.save(form); // form из первого рендера!
}, []);
```

`useCallback` не лечит stale closure — он его **создаёт**, если зависимости неполные.
Мемоизированная функция держит значения того рендера, в котором была создана.

## Асинхронность: «старые» значения после await

```jsx
const handleSubmit = async () => {
  await api.save(draft);
  if (draft === initialDraft) { … } // сравнение со значениями момента клика
};
```

Иногда это желаемое поведение (данные момента действия), иногда — баг. Важно понимать:
после `await` вы всё ещё в замыкании того рендера. Свежее значение — через ref.

## Классовые компоненты: обратная проблема

В классах `this.state` и `this.props` — изменяемые поля экземпляра, поэтому колбэк всегда
читает **свежие** значения. Это порождало обратный баг: посреди асинхронной операции
пропсы менялись («показать профиль пользователя 1», а через секунду `this.props.user` уже 2).
Снапшоты функциональных компонентов делают поведение предсказуемым, ценой stale closures.
