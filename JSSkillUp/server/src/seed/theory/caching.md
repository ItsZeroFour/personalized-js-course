# Кеширование

## HTTP-кеш: Cache-Control

Заголовок ответа `Cache-Control` говорит браузеру и промежуточным кешам (CDN), что можно
делать с ответом:

- **`max-age=N`** — ответ свежий N секунд, в течение них браузер берёт его из кеша
  без запроса;
- **`no-cache`** — хранить можно, но **перед каждым использованием ревалидировать**
  у сервера;
- **`no-store`** — не сохранять вообще (приватные данные);
- **`public` / `private`** — можно ли кешировать на общих кешах (CDN) или только в браузере;
- **`immutable`** — ресурс никогда не изменится, не ревалидировать даже при перезагрузке;
- **`stale-while-revalidate=N`** — N секунд можно отдавать устаревший ответ, обновляя его в фоне.

## Ревалидация: ETag и If-None-Match

```
← 200 OK
  ETag: "a1b2c3"
  Cache-Control: no-cache

→ GET /index.html
  If-None-Match: "a1b2c3"

← 304 Not Modified         (без тела — экономия трафика)
```

`ETag` — идентификатор версии ресурса (хеш содержимого). Альтернатива — `Last-Modified`
+ `If-Modified-Since` (точность до секунды).

## Хеши в именах файлов и вечный кеш

Стратегия для SPA:

| Файл | Заголовок |
| --- | --- |
| `assets/app.3f9a1c.js`, `styles.a81b.css`, шрифты, картинки сборки | `public, max-age=31536000, immutable` |
| `index.html` | `no-cache` (+ ETag) |

Сборщик добавляет в имя **хеш содержимого**: изменился код — изменилось имя. Поэтому
файл с данным именем можно кешировать навсегда. `index.html` всегда ревалидируется
и после деплоя ссылается на новые имена.

Подвох: у пользователя с открытой вкладкой старый `index.html`, и lazy-чанки грузятся по
старым именам. Если после деплоя старые файлы удалены — **ChunkLoadError**. Решения:
хранить предыдущие сборки какое-то время; ловить ошибку загрузки чанка и перезагружать
страницу.

## Service Worker и офлайн

Service Worker — скрипт-прокси между страницей и сетью. Перехватывает `fetch` и решает,
откуда отдать ответ:

- **cache first** — статика приложения, офлайн-режим;
- **network first** — данные, которые важно видеть свежими, с запасным вариантом из кеша;
- **stale-while-revalidate** — отдать из кеша сразу, обновить в фоне.

Основа PWA. Обычно не пишется руками: Workbox, `vite-plugin-pwa`. Главная сложность —
обновление: новый Service Worker ждёт закрытия всех вкладок; без продуманной стратегии
пользователи «застревают» на старой версии.

## Клиентские хранилища

| | Объём | Время жизни | Доступ | Отправляется на сервер |
| --- | --- | --- | --- | --- |
| **cookies** | ~4 КБ | до `Expires`/`Max-Age` или сессия | JS (если не `HttpOnly`) | с каждым запросом на домен |
| **localStorage** | ~5–10 МБ | бессрочно | синхронный JS API, строки | нет |
| **sessionStorage** | ~5 МБ | до закрытия вкладки | как localStorage, своя вкладка | нет |
| **IndexedDB** | сотни МБ и больше | бессрочно | асинхронный, объекты, индексы, транзакции | нет |
| **Cache API** | квота origin | бессрочно | пары запрос/ответ, для Service Worker | нет |

Правила:

- `localStorage` — **синхронный**, блокирует main thread: не для больших данных;
  хранит только строки (`JSON.stringify`); доступен любому скрипту на странице — не место
  для токенов;
- **IndexedDB** — для больших объёмов и офлайн-данных (обычно через обёртки `idb`, Dexie);
- cookies — для того, что должен видеть сервер (сессия), с флагами `HttpOnly`, `Secure`,
  `SameSite`;
- событие `storage` сообщает другим вкладкам об изменении localStorage — способ
  синхронизации (или `BroadcastChannel`).
