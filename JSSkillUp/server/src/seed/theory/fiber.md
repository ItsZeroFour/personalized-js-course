# Fiber-архитектура

## Зачем понадобился Fiber

До React 16 reconciler был **рекурсивным** (stack reconciler): начав обход дерева, он не
мог остановиться до конца. Большое обновление — например, перерисовка длинного списка —
занимало main thread на сотни миллисекунд. Всё это время браузер не обрабатывал ввод
и не рисовал кадры: интерфейс «замерзал».

Fiber (React 16) переписал ядро так, чтобы работу можно было **разбить на части,
приостановить, возобновить, отменить и приоритизировать**. На этом построены все
concurrent-возможности React 18+.

## Fiber-узел

Fiber — это объект, соответствующий одному элементу дерева (компоненту, DOM-узлу,
фрагменту). Упрощённо в нём лежит:

- `type`, `key` — что за элемент;
- `child`, `sibling`, `return` — ссылки на первого ребёнка, соседа и родителя.
  Дерево превращено в связный список, который можно обходить **циклом**, а не рекурсией;
- `pendingProps` / `memoizedProps` — новые и прошлые пропсы;
- `memoizedState` — для функциональных компонентов это **связный список хуков**
  (отсюда правила хуков);
- `updateQueue` — очередь обновлений;
- `flags` — какие изменения нужно применить при коммите (вставка, обновление, удаление);
- `lanes` — приоритет запланированной работы;
- `alternate` — ссылка на «двойника» в другом дереве.

## current и workInProgress

React держит **два дерева**:

- **current** — то, что сейчас отображено на экране;
- **workInProgress** — строящееся новое дерево.

Рендер работает над workInProgress, не трогая current. Если работу нужно прервать
или выбросить, экран остаётся согласованным. При коммите деревья меняются ролями
(double buffering, как в графике): workInProgress становится current.

## Work loop

Упрощённо рендер — это цикл:

```js
while (workInProgress !== null && !shouldYield()) {
  workInProgress = performUnitOfWork(workInProgress);
}
```

Единица работы — один fiber: вызвать компонент, сравнить детей, перейти к следующему
узлу. В concurrent-режиме `shouldYield()` проверяет, не пора ли отдать управление
браузеру (примерно каждые 5 мс). Если пора — цикл прерывается и продолжится в следующей
задаче. Если за это время пришло более срочное обновление, текущая работа может быть
выброшена и начата заново.

**Коммит не прерывается никогда**: пользователь не должен увидеть наполовину
обновлённый интерфейс.

## Приоритеты и lanes

Обновления имеют приоритет — **lane** (битовая маска):

- **SyncLane** — дискретные события: клик, нажатие клавиши. Обрабатываются немедленно;
- **InputContinuousLane** — непрерывные: скролл, mousemove;
- **DefaultLane** — обычные обновления (ответ сети и т. п.);
- **TransitionLanes** — обновления в `startTransition`, прерываемые;
- **IdleLane** — самые низкие.

Пример: пользователь печатает в поле фильтра, а список фильтруется в transition.
Нажатие клавиши (SyncLane) прерывает тяжёлый рендер списка, поле обновляется сразу,
а список дорендерится потом.

## Почему рендер должен быть чистым

Раз рендер может быть **вызван несколько раз, прерван или выброшен**, функция
компонента обязана быть чистой: при тех же пропсах и state возвращать тот же результат
и не иметь побочных эффектов.

```jsx
let renders = 0;
function Counter() {
  renders++;              // побочный эффект в рендере — число непредсказуемо
  fetch('/api/track');    // запрос уйдёт столько раз, сколько React вызовет функцию
  return <p>{renders}</p>;
}
```

Побочные эффекты — в обработчиках событий и в `useEffect`. StrictMode в dev специально
вызывает компоненты дважды, чтобы такие ошибки проявлялись сразу. React Compiler тоже
полагается на чистоту: иначе автоматическая мемоизация изменит поведение.

## Как это спрашивают

- «Что такое Fiber и зачем он?» — прерываемый рендер, приоритеты, основа concurrent
  features. Слабый ответ: «новый Virtual DOM».
- «Чем render phase отличается от commit phase? Что из них можно прервать?»
- «Почему в рендере нельзя делать запросы и мутировать внешние переменные?»
- «Зачем StrictMode дважды вызывает компоненты?»
- Вопрос со звёздочкой: «как React понимает, что пора уступить браузеру?» — Scheduler,
  квант около 5 мс, `MessageChannel` для планирования задач.
