# Структура проекта и FSD

## По типам против по фичам

**По типам файлов:**

```
src/
  components/   Button.tsx, UserCard.tsx, CartItem.tsx, CheckoutForm.tsx …
  hooks/        useUser.ts, useCart.ts …
  api/          users.ts, cart.ts …
  utils/
```

Удобно на старте, но с ростом проекта код **одной фичи размазан** по пяти папкам;
`components/` превращается в свалку из сотни файлов; непонятно, что можно удалить.

**По фичам (доменам):**

```
src/
  features/
    cart/        CartItem.tsx, useCart.ts, cartApi.ts, cart.test.ts, index.ts
    checkout/
  shared/        ui-kit, утилиты, api-клиент
```

Код, который меняется вместе, лежит вместе (**colocation**). Фичу легко найти, изменить
и удалить целиком.

## Feature-Sliced Design

FSD — формализованная методология структуры фронтенда. Три уровня:

**Слои** (сверху вниз):

| Слой | Что содержит |
| --- | --- |
| `app` | инициализация: провайдеры, роутер, глобальные стили |
| `pages` | страницы — композиция виджетов и фич под маршрут |
| `widgets` | крупные самостоятельные блоки: шапка, лента, сайдбар |
| `features` | пользовательские действия с ценностью: добавить в корзину, оставить отзыв, войти |
| `entities` | бизнес-сущности: user, product, order — модель, API, UI-карточка |
| `shared` | переиспользуемое без бизнес-логики: ui-kit, api-клиент, lib, config |

**Слайсы** — деление слоя по доменам: `entities/user`, `entities/product`,
`features/add-to-cart`.

**Сегменты** — деление слайса по назначению: `ui`, `model` (state, логика), `api`, `lib`, `config`.

## Правило направления зависимостей

Модуль может импортировать **только из слоёв ниже**:
`pages` → `widgets` → `features` → `entities` → `shared`.

- `shared` не знает о бизнесе;
- `entities/user` не импортирует `features/auth`;
- **слайсы одного слоя не импортируют друг друга** — `features/cart` не знает о
  `features/wishlist`. Связь собирается уровнем выше.

Это ограничивает связанность: изменение или удаление фичи не ломает соседей, нет
циклических зависимостей. Проверяется автоматически: Steiger (линтер FSD),
`eslint-plugin-boundaries`, `import/no-restricted-paths`.

Если двум фичам нужна общая логика — она опускается ниже (в `entities` или `shared`),
а не импортируется «вбок».

## Публичный API модуля

Каждый слайс наружу отдаёт только `index.ts`:

```ts
// entities/user/index.ts
export { UserCard } from './ui/UserCard';
export { useCurrentUser } from './model/useCurrentUser';
export type { User } from './model/types';
```

```ts
import { UserCard } from '@/entities/user';            // можно
import { UserCard } from '@/entities/user/ui/UserCard'; // глубокий импорт — нельзя
```

Внутренности можно переписывать, не трогая потребителей. Минус barrel-файлов —
возможное ухудшение tree shaking и циклы импортов при неаккуратности; держите их
тонкими.

## Когда FSD избыточен

- небольшое приложение, лендинг, прототип, 5–10 экранов, один разработчик;
- команда не знакома с методологией, а сроки горят — споры «это feature или entity?»
  съедят больше времени, чем принесут пользы.

Упрощённый вариант, который масштабируется: `app/`, `pages/`, `features/`, `shared/` +
правило однонаправленных зависимостей и публичный API. Переход к полному FSD — когда
границы действительно начали размываться.
