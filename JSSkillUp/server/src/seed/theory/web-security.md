# XSS, CSRF и безопасность фронтенда

## XSS: выполнение чужого скрипта на вашей странице

Если атакующий смог выполнить JS в контексте вашего сайта, он может всё, что может
пользователь: читать данные страницы и `localStorage`, отправлять запросы от его имени,
подменять интерфейс (фишинг поверх настоящей страницы).

Виды:

- **Stored** — вредоносный код сохранён на сервере (комментарий, имя профиля) и показан
  всем, кто откроет страницу. Самый опасный.
- **Reflected** — код в параметре запроса, сервер вставляет его в ответ
  (`/search?q=<script>…`). Жертва переходит по подготовленной ссылке.
- **DOM-based** — уязвимость целиком на клиенте: JS берёт данные из `location.hash`,
  `postMessage`, `localStorage` и вставляет в DOM небезопасно.

## Почему React защищает и где дыра

JSX **экранирует** значения: `<p>{comment}</p>` вставляет текстовый узел, `<script>`
в строке останется текстом. Это закрывает большинство случаев.

Где защита не работает:

```jsx
<div dangerouslySetInnerHTML={{ __html: userBio }} />   // HTML как есть
<a href={user.website}>сайт</a>                          // javascript:alert(document.cookie)
ref.current.innerHTML = userData;                         // обход React
eval(userCode); new Function(userCode);                   // выполнение строки
```

- HTML от пользователя (редактор, markdown) — только через санитайзер: **DOMPurify**.
- URL от пользователя — проверять протокол: разрешать только `http:`, `https:`, `mailto:`.
  React 19 блокирует `javascript:` URL, но полагаться стоит на свою валидацию.
- SSR: данные, встраиваемые в `<script>` для гидрации, нужно сериализовать с экранированием
  `</script>`.
- Сторонние скрипты и npm-зависимости — тоже поверхность атаки (supply chain).

## Content Security Policy

CSP — заголовок, ограничивающий, откуда страница может загружать и выполнять ресурсы:

```
Content-Security-Policy: default-src 'self'; script-src 'self' 'nonce-r4nd0m'; img-src 'self' https://cdn.example.com; object-src 'none'; base-uri 'self'
```

- инлайн-скрипты и `eval` запрещены (без `'unsafe-inline'`/`'unsafe-eval'`);
- разрешённые скрипты — со своего домена или с одноразовым `nonce`;
- даже если XSS-инъекция случилась, внедрённый скрипт не выполнится.

Внедрять начинают с `Content-Security-Policy-Report-Only` и сбора отчётов.

## CSRF: запрос от имени пользователя

Пользователь залогинен на `bank.com` (сессия в cookie). Он открывает `evil.com`, где есть:

```html
<form action="https://bank.com/transfer" method="POST">
  <input name="to" value="attacker"><input name="amount" value="10000">
</form>
<script>document.forms[0].submit()</script>
```

Браузер отправит запрос **с cookies bank.com**. Атакующий не видит ответа, но действие
выполнено.

Защита:

- **`SameSite` cookies**: `Lax` (по умолчанию в современных браузерах) — cookie не
  отправляется с кросс-сайтовыми POST; `Strict` — вообще ни с какими кросс-сайтовыми
  запросами;
- **CSRF-токен**: случайное значение в форме или заголовке; чужой сайт не может его прочитать;
- проверка `Origin`/`Referer` на сервере;
- изменяющие действия — не через GET.

CORS от CSRF **не защищает**: «простой» POST отправляется и без разрешения CORS.

## Где хранить JWT

| Вариант | XSS | CSRF |
| --- | --- | --- |
| `localStorage` / `sessionStorage` | **уязвимо**: любой внедрённый скрипт прочитает токен и уведёт | не уязвимо: токен не прикладывается сам |
| cookie `HttpOnly; Secure; SameSite` | токен не украсть (JS не читает), но XSS может действовать от имени пользователя, пока страница открыта | нужна защита: SameSite, CSRF-токен |
| память (переменная) | не переживает перезагрузку; XSS может перехватить | не уязвимо |

Распространённая схема: **короткоживущий access-токен в памяти** + **refresh-токен в
`HttpOnly; Secure; SameSite=Strict` cookie** на отдельный путь (`/auth/refresh`).
После перезагрузки страница получает новый access-токен по refresh.

Почему «не в localStorage»: XSS обходит почти любую защиту, но с `HttpOnly` cookie
атакующий хотя бы не уносит долгоживущий токен с собой.

## Прочие заголовки и практики

- `Strict-Transport-Security` — только HTTPS;
- `X-Content-Type-Options: nosniff`;
- `frame-ancestors` в CSP (или `X-Frame-Options`) — защита от clickjacking;
- `rel="noopener noreferrer"` для внешних ссылок с `target="_blank"` (современные браузеры
  делают noopener по умолчанию);
- аудит зависимостей (`npm audit`, Dependabot), lock-файл, минимум сторонних скриптов.
