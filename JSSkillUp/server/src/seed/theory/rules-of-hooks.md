# Правила хуков

## Два правила

1. **Вызывать хуки только на верхнем уровне** компонента или кастомного хука.
   Не внутри условий, циклов, вложенных функций, после раннего `return`,
   не в `try/catch/finally`.
2. **Вызывать хуки только из React-функций**: функциональных компонентов и кастомных
   хуков. Не из обычных функций, классов, обработчиков событий, колбэков
   `useEffect`/`useMemo`/`useReducer`.

Исключение — `use` из React 19: его можно вызывать условно (но только в компоненте или хуке).

## Список хуков на fiber-узле

У хуков нет имён. React хранит их состояние в **связном списке** на fiber компонента
(`memoizedState`) и при каждом рендере проходит по нему **по порядку вызова**:

```jsx
function Form() {
  const [name, setName] = useState('');     // хук №1
  const [email, setEmail] = useState('');   // хук №2
  useEffect(() => { … }, [name]);           // хук №3
}
```

На втором рендере первый вызов `useState` получит состояние хука №1, второй — №2 и т. д.
Порядок — единственный способ сопоставления.

## Что сломается при условном вызове

```jsx
function Profile({ user }) {
  if (!user) return null;                 // ранний return ДО хуков
  const [tab, setTab] = useState('info');
  …
}
```

Первый рендер с `user = null`: хуков ноль. Второй с `user`: хук появился — React
видит больше хуков, чем в прошлый раз, и падает с ошибкой
«Rendered more hooks than during the previous render». Обратная ситуация —
«Rendered fewer hooks than expected».

Ещё опаснее, когда число хуков совпадает, а порядок нет:

```jsx
if (isEditing) {
  const [draft, setDraft] = useState(''); // то есть, то нет
}
const [count, setCount] = useState(0);    // получит state draft'а!
```

Правильно: все хуки в начале, условия — внутри хуков или после них:

```jsx
function Profile({ user }) {
  const [tab, setTab] = useState('info');
  if (!user) return null;
  …
}

useEffect(() => {
  if (!isEditing) return; // условие внутри эффекта
  …
}, [isEditing]);
```

## Правило зависимостей

`react-hooks/exhaustive-deps` требует, чтобы все значения из рендера, используемые
в `useEffect`, `useLayoutEffect`, `useMemo`, `useCallback`, были в массиве зависимостей.
Нарушение = stale closure.

Когда его «нарушают» осознанно — почти никогда. Если зависимость мешает, код
реструктурируют:

- объект или функцию, не зависящие от пропсов и state, — вынести из компонента;
- функцию, нужную только эффекту, — объявить внутри эффекта;
- обновление на основе предыдущего state — функциональная форма, тогда state не нужен
  в зависимостях;
- «прочитать последнее значение, не реагируя на его изменение» — ref или `useEffectEvent`.

`// eslint-disable-next-line react-hooks/exhaustive-deps` — сигнал на ревью, что нужно
объяснение.

## Что проверяет линтер

`eslint-plugin-react-hooks`:

- **`rules-of-hooks`** — хуки не в условиях и не вне компонентов/хуков. Компонентом
  считается функция с заглавной буквы, хуком — с префикса `use`;
- **`exhaustive-deps`** — полнота зависимостей;
- в новых версиях (рекомендованная конфигурация 6+/7) — правила React Compiler:
  чистота рендера, запрет на чтение ref в рендере, `setState` синхронно в эффекте,
  мутации пропсов и state.

## Почему такой дизайн

Альтернатива — именованные хуки (`useState('name', '')`) — порождает коллизии имён при
композиции кастомных хуков. Порядковый подход позволяет свободно вызывать один хук
несколько раз и вкладывать хуки друг в друга. Цена — правила, которые проверяет линтер.

## Как это спрашивают

- «Какие правила хуков вы знаете и почему они такие?» — ждут объяснение через порядок.
- «Что не так с этим кодом?» — хук после раннего `return` или внутри `if`.
- «Можно ли вызвать хук в обработчике клика? В цикле?»
- «Что делать, если линтер требует добавить зависимость, а эффект начинает срабатывать
  слишком часто?»
