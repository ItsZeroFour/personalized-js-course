# Локальный и глобальный стейт

## Сначала — какой это стейт

Вопрос «Redux или Zustand?» задают слишком рано. Сначала нужно понять, **какого вида**
состояние, — от этого зависит место хранения.

| Вид | Примеры | Где хранить |
| --- | --- | --- |
| **Серверное** | списки, профиль, заказы | TanStack Query / RTK Query / SWR |
| **URL** | фильтры, сортировка, страница, вкладка, id открытой сущности | path и search params |
| **Форма** | значения полей, ошибки, touched | локальный state или React Hook Form |
| **Локальное UI** | открыт ли дропдаун, наведение, анимация | `useState` в компоненте |
| **Глобальное клиентское** | тема, текущий пользователь, корзина, редактор | Context / Zustand / Redux |

**Серверное состояние** — это кеш чужих данных: у него есть устаревание, повторные
запросы, инвалидация, общий доступ из многих мест. Класть его в Redux-слайс с ручными
`loading/error` — самая частая архитектурная ошибка. Когда серверные данные уходят в кеш
запросов, «глобального состояния» обычно остаётся совсем немного.

## Подъём состояния и prop drilling

Если два компонента должны видеть одно значение, state поднимают **до ближайшего общего
родителя** и передают вниз пропсами. Это нормальный, базовый путь React.

**Prop drilling** — когда значение проходит через 4–5 уровней компонентов, которым оно
не нужно. Решения по возрастанию «тяжести»:

1. **Композиция**: передать готовый элемент через `children` или проп-слот, а не данные
   для него. Промежуточные компоненты вообще перестают знать о значении.
2. **Context** для редко меняющихся данных.
3. **Стор** для часто меняющихся и сложных.

```jsx
// вместо Layout → Header → UserMenu → Avatar(user)
<Layout header={<Header right={<UserMenu user={user} />} />} />
```

## Колокация состояния

Держите state **как можно ближе** к месту использования. Чем выше state, тем больше
компонентов перерисовывается при его изменении и тем труднее понять, кто его меняет.

Признаки, что state слишком высоко: страница перерисовывается при вводе в поле поиска;
в корневом компоненте десятки `useState`, не связанных между собой.

## Состояние в URL как источник правды

Фильтры и пагинация в URL дают бесплатно:

- переживают перезагрузку;
- ссылкой можно поделиться;
- работают «Назад» и «Вперёд»;
- аналитика видит, что ищут пользователи.

```jsx
const [searchParams, setSearchParams] = useSearchParams();
const page = Number(searchParams.get('page') ?? 1);
const setPage = (next) =>
  setSearchParams((prev) => { prev.set('page', String(next)); return prev; });
```

Дублировать значение из URL в `useState` не нужно — URL и есть state. Для частых
изменений (ввод в поиск) — debounce перед записью в URL и `replace` вместо `push`,
чтобы не засорять историю.

## Когда нужен глобальный стор

- много **несвязанных** компонентов читают и меняют одно клиентское состояние
  (корзина до оформления, открытые вкладки редактора, настройки плеера);
- состояние меняется **часто**, а читают его по частям — нужны селекторы;
- сложная доменная логика, которую удобно держать вне компонентов и тестировать отдельно;
- нужны DevTools, журнал действий, persist, undo.

Не нужен: чтобы «было удобно достать откуда угодно» данные, которые на самом деле
серверные или локальные.

## Как это спрашивают

- «Где вы храните состояние и как решаете, куда его положить?» — главный вопрос блока.
- «Что такое prop drilling и как с ним бороться?» — сильный ответ начинается
  с композиции, а не с Redux.
- «Почему фильтры лучше хранить в URL?»
- «Нужен ли Redux, если есть TanStack Query?»
