# Рендеринг и reconciliation

## Что значит «компонент отрендерился»

**Рендер** — React вызвал функцию компонента и получил дерево React-элементов
(обычные объекты `{ type, props, key }`). Это ещё не изменение DOM.

Обновление интерфейса проходит две фазы:

1. **Render phase** — React вызывает компоненты, строит новое дерево и сравнивает его
   со старым (**reconciliation**). DOM не трогается. Фаза может быть прервана и повторена.
2. **Commit phase** — React применяет вычисленные изменения к DOM, заполняет ref, вызывает
   layout-эффекты. Затем браузер рисует кадр, и после этого выполняются `useEffect`.

Отсюда главное следствие: **ререндер ≠ изменение DOM**. Компонент может отрендериться
десять раз, а DOM не изменится ни разу, если результат тот же.

## Когда компонент рендерится

Ровно три причины:

- изменился **его state** (`setState` со значением, отличным по `Object.is`);
- перерисовался **родитель**;
- изменилось значение **контекста**, который он читает.

«Изменились пропсы» — не отдельная причина: пропсы меняются только потому, что
перерисовался родитель. И наоборот: **при ререндере родителя по умолчанию перерисовываются
все его дети**, даже с теми же пропсами. Это не баг, а стратегия: сравнивать пропсы тоже
стоит времени, а рендер обычно дешёвый. `memo` меняет правило для конкретного компонента.

## Virtual DOM: что это и чего это не значит

Virtual DOM — дерево лёгких JS-объектов, описывающих интерфейс. React сравнивает
новое дерево со старым и вносит в настоящий DOM только разницу.

Частый миф: «Virtual DOM быстрее DOM». Прямые точечные изменения DOM быстрее любого
диффа. Ценность Virtual DOM в другом: **декларативность** — вы описываете, каким должен
быть интерфейс при данном state, а React сам вычисляет, как привести к нему DOM.
Производительность «достаточно хорошая» без ручной работы.

## Эвристики сравнения (diffing)

Общий алгоритм сравнения двух деревьев — O(n³). React использует две эвристики и
работает за O(n):

**1. Разный тип → поддерево пересоздаётся.**

```jsx
// было              // стало
<div><Counter /></div>   <section><Counter /></section>
```

`div` → `section`: React размонтирует всё старое поддерево (вызовет cleanup эффектов,
потеряет state `Counter`) и смонтирует новое. То же для компонентов: `<Counter>` →
`<Timer>` в той же позиции — пересоздание.

**2. Тот же тип → обновление на месте.** Для DOM-элемента меняются только изменившиеся
атрибуты; для компонента тот же экземпляр получает новые пропсы, **state сохраняется**.

**3. Дети сопоставляются по `key`** (или по позиции, если ключей нет) — подробнее в теме
«Keys и списки».

### State привязан к позиции в дереве

```jsx
function App({ isPro }) {
  return isPro ? <Counter /> : <Counter />;
}
```

При смене `isPro` state `Counter` **сохранится**: в той же позиции тот же тип.
А вот так — сбросится:

```jsx
return isPro ? <Counter key="pro" /> : <Counter key="free" />;
```

## Никогда не объявляйте компонент внутри компонента

```jsx
function List({ items }) {
  function Row({ item }) {           // новая функция на каждом рендере
    const [open, setOpen] = useState(false);
    return <li onClick={() => setOpen(!open)}>{item.title}</li>;
  }
  return items.map((item) => <Row key={item.id} item={item} />);
}
```

Каждый рендер `List` создаёт **новый тип** `Row`. Для React это другой компонент:
все строки размонтируются и монтируются заново, state `open` теряется, фокус слетает.
Компонент объявляется на верхнем уровне модуля.

## Композиция как оптимизация: `children`

```jsx
function Layout({ children }) {
  const [menuOpen, setMenuOpen] = useState(false);
  return (
    <div>
      <Header onToggle={() => setMenuOpen((v) => !v)} />
      {children}
    </div>
  );
}

<Layout>
  <ExpensivePage />
</Layout>
```

При открытии меню `Layout` перерисуется, но `<ExpensivePage />` — **нет**. Элемент
`children` создан в родителе `Layout`, и между рендерами это тот же объект. React видит
тот же элемент и пропускает поддерево. Это часто решает проблему производительности
без единого `memo`.

Второй приём того же рода — **опустить state вниз**: если state нужен только кнопке,
пусть он живёт в кнопке, а не в странице.

## Как это спрашивают

- «Что такое Virtual DOM и reconciliation?» — две фазы, эвристики O(n), роль `key`.
  Слабый ответ: «Virtual DOM быстрее DOM».
- «Почему компонент перерисовался, если пропсы не менялись?» — рендер родителя.
- «Что будет с state, если условно рендерить один и тот же компонент?» — сохраняется,
  если тот же тип в той же позиции.
- «Почему нельзя объявлять компонент внутри компонента?»
- «Как оптимизировать без memo?» — опустить state, передать поддерево как `children`.
